# Documentation guidelines

## Functional documentation (what the system does)
- Location: `docs/functional/`
- Audience: users and non-technical readers.
- Describe each feature from the user's point of view: the problem it
  solves, how to use it (filters, searches) and concrete examples of
  input and expected result.
- Keep a glossary (CVE, CVSS, EPSS, KEV, severity) and explain every
  field shown on screen.
- Avoid implementation jargon.

## Technical documentation (how it works)
- Location: `docs/technical/` and `README.md`
- Audience: developers.
- Must include:
  - Architecture and data flow (external source -> API -> frontend).
  - Data model and how each source is normalized.
  - How ingestion works: schedule, rate limits, retries, cache.
  - How to install, configure (environment variables), run and test.
  - Important design decisions as ADRs in `docs/technical/adr/`.
- Endpoints are documented through OpenAPI (autogenerated). Every endpoint
  needs a summary, a description and example responses.
- Every module and public function has a docstring covering purpose,
  parameters, return value and possible errors.
- Comments explain "why", not "what".

## When finishing a task
State which documentation was updated, or why none was needed.
